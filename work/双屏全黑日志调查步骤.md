# PVM/GVM 双屏全黑日志调查步骤

## 1. 适用范围

本文用于排查以下架构中的“仪表屏与中控屏同时黑屏”问题：

```text
PVM Linux + qcrosvm/Gunyah + GVM Android
```

- 仪表侧主要运行在 PVM Linux。
- 中控侧主要运行在 GVM Android。
- PVM 与 GVM 共用 SoC、Hypervisor、部分显示后端、显示硬件和电源链路。
- MCU 负责或参与 ACC、唤醒、SoC 上下电等控制。

两个屏幕同时黑屏时，应优先调查共同故障域，不能直接按 Android/SystemUI 黑屏处理。

```text
MCU / PMIC / SoC 供电
          |
          v
       PVM Linux -------- 仪表应用/仪表画面
          |
          +-------------- display/openwfd/SerDes/背光
          |
          +-------------- qcrosvm/Gunyah
                              |
                              v
                          GVM Android -------- 中控画面
```

## 2. 调查目标

每次调查必须回答以下问题：

1. 两个屏幕是被软件正常关闭，还是在 ON 状态下失去物理显示？
2. 黑屏后 MCU、PVM、GVM 分别是否仍在运行？
3. GVM 是否被 qcrosvm/Gunyah 暂停、停止、崩溃或重新创建？
4. PVM 是否进入 suspend、崩溃、卡死或突然失电？
5. MCU 是否保持运行、重启，或者主动执行了 SoC OFF/ON？
6. 恢复操作使旧系统恢复运行，还是触发了 MCU/SoC/PVM/GVM 的完整重启？
7. 证据能够证明哪一种根因，哪些只能保留为可能性？

## 3. 基本证据规则

### 3.1 只从原始日志建立结论

- 不直接继承测试报告或旧分析中的结论。
- 文件名时间、压缩包生成时间和文件修改时间只能辅助定位，不能替代日志事件时间。
- 每一个关键结论必须附“日志文件名 + 行号 + 原始日志”。
- 数值型状态必须查询源码、IDL、DBC 或枚举表，不能凭数值大小猜测语义。

例如：

- `Outside lock: 0` 中的 `0` 是 `NoRequest`，不表示解锁。
- `DoorlockNotify: lockStatus=0` 使用另一套枚举，其中 `0` 表示已闭锁。

### 3.2 区分已证实、推断和未知

- **已证实**：有直接原始日志证明。
- **强支持**：多个独立日志源的时间和状态相互吻合。
- **可能**：机制成立，但关键时间窗口缺少对应模块日志。
- **不能确认**：现有日志无法区分多个原因。
- **已排除**：存在明确反证。

不能因为某类日志“没有找到”就直接排除某条路径。必须先确认对应日志文件完整覆盖了故障窗口。

### 3.3 区分软件确认和物理状态

例如：

```text
Screen confirmed state: ON
```

只能证明软件请求得到确认，不能证明以下物理条件已经成立：

- 面板已经出图；
- 背光已经点亮；
- SerDes 链路正常；
- 显示供电正常；
- 用户实际看到了画面。

## 4. 第一步：保护现场并清点日志

### 4.1 保留原始文件

- 不直接修改、重新压缩或覆盖原始日志。
- 解压分析应在单独的临时目录进行。
- 必要时记录原始文件的大小和 SHA-256。
- 检查压缩包是否损坏、是否只收集了部分目录。

### 4.2 建立日志清单

至少检查以下日志源：

| 域 | 重点日志 |
| --- | --- |
| MCU | `mcu.log`、MCU 串口日志、PMIC/看门狗/reset/power 日志 |
| PVM | syslog/journal、kernel/dmesg、pstore、powermgr、rpcd、coreservice、Tuanjie、openwfd/display、qcrosvm/Gunyah |
| GVM | logcat 各 buffer、kernel/dmesg、pstore、tombstones、ANR、DropBox、`ivi_la_gvm*.tar.gz` |
| 外部证据 | 测试时间、视频、操作步骤、CAN Trace、示波器/电源波形 |

同时记录以下现场信息；没有也不应阻塞日志分析：

- 黑屏的大致时间和允许误差；
- 是无背光，还是有背光但无画面；
- 音频、语音、蓝牙、倒车影像是否仍工作；
- 锁车、解锁、开门、上车和方控重启的操作时间；
- 恢复后是否出现开机动画。

## 5. 第二步：划分旧实例和新实例

必须先把“故障前旧实例”和“恢复后的新实例”分开。

可使用以下标志识别新实例：

- kernel boot banner、`Linux version`；
- boot ID 变化；
- Android `BOOT_COMPLETED`、zygote/system_server 新 PID；
- qcrosvm 创建新 VM；
- MCU 内部计数重新从零开始；
- MCU 重新打印初始化和 SoC 上电流程。

新启动阶段的 reset 日志只用于确认发生了新启动或 MCU 重新执行了流程，不能自动当作旧实例的故障原因。Hypervisor 没有向 PVM/GVM 传递启动原因时，PVM/GVM 新启动日志尤其不能用于反推旧系统为何停止。

## 6. 第三步：寻找各域真正的最后日志

### 6.1 不只检查一个文件

分别寻找以下日志源在旧实例中的最大有效事件时间：

- MCU；
- PVM 聚合 syslog；
- PVM kernel；
- PVM Tuanjie；
- PVM qcrosvm/Gunyah；
- PVM display/openwfd；
- GVM logcat；
- GVM kernel/pstore；
- 其他独立持久化日志。

PVM 的某个聚合 syslog 提前结束，不等于 PVM 已停止。若 Tuanjie、kernel 或其他进程仍有更晚日志，应以各日志源的实际覆盖范围分别描述。

### 6.2 检查异常终止特征

- 最后一行是否完整；
- 是否被 NUL 截断；
- 是否存在大量日志尚未刷盘；
- 是否发生日志轮转；
- 是否存在正常 shutdown/suspend 尾部序列；
- 最后几十行是否显示 panic、watchdog、I/O、display 或 VM 错误。

建立终点矩阵：

| 域/日志源 | 旧实例最后时间 | 文件名和行号 | 最后一条原始日志 | 结束性质 |
| --- | --- | --- | --- | --- |
| MCU | 待填写 | 待填写 | 待填写 | 连续/重启/缺口 |
| PVM syslog | 待填写 | 待填写 | 待填写 | 正常/截断/轮转 |
| PVM Tuanjie | 待填写 | 待填写 | 待填写 | 正常/突然停止 |
| PVM kernel | 待填写 | 待填写 | 待填写 | 正常/异常 |
| GVM logcat | 待填写 | 待填写 | 待填写 | 正常/突然停止 |
| GVM kernel | 待填写 | 待填写 | 待填写 | 正常/异常 |

## 7. 第四步：对齐 MCU、PVM、GVM 时钟

不要假设三套墙上时间完全一致。应使用跨域共同事件校准，例如：

- ACC/HACC ON、OFF；
- UsageMode 变化；
- `Outside lock:2 -> 0`；
- `STANDBY_ALARM`、`NORMALMODE`；
- GVM VHAL power property；
- MCU `Wakeup source`；
- 主屏 OFF/ON 请求。

需要区分：

- 事件发生时间；
- MCU 内部 tick；
- PVM/GVM monotonic 时间；
- 日志落盘时间；
- 消息 payload 中携带的原始时间。

MCU 日志可能经过 rpcd 或其他聚合器延迟落盘，因此不能把墙上时间最接近的一条 MCU 日志直接认定为 GVM 事件的触发源。

建议建立时钟对齐表：

| 对齐事件 | MCU 时间 | PVM 时间 | GVM 时间 | 估计偏差/延迟 |
| --- | --- | --- | --- | --- |
| ACC OFF | 待填写 | 待填写 | 待填写 | 待填写 |
| 锁车 | 待填写 | 待填写 | 待填写 | 待填写 |
| 返车唤醒 | 待填写 | 待填写 | 待填写 | 待填写 |

## 8. 第五步：重建故障时间线

以故障时间前后至少两分钟为初始范围；若涉及待机、GuardMode 或定时动作，应进一步扩大窗口。

时间线统一使用以下格式：

| 时间 | 域 | 事件 | 证据含义 | 日志文件名＋行号：原始日志 |
| --- | --- | --- | --- | --- |
| 待填写 | MCU/PVM/GVM | 待填写 | 待填写 | 待填写 |

重点阶段包括：

1. 泊车或其他前置业务是否正常结束；
2. 下电条件何时出现；
3. 屏幕 OFF 请求是否正常执行；
4. 锁车事件及门锁反馈；
5. PVM 是否进入 Standby/Guard/STR；
6. 返车/开门/ACC ON 是否到达 MCU、PVM、GVM；
7. 两个屏幕是否收到 ON 请求；
8. 旧 PVM、旧 GVM 分别何时失去日志；
9. MCU 是否执行复位或 SoC 电源循环；
10. 恢复后的完整启动顺序。

## 9. 第六步：检查 MCU 和 SoC 电源链路

重点搜索：

```text
accon
Hacc
nmMode
nmState
Wakeup source
SOC ON
SOC OFF
SOC Pwr ON Over
after B21
ResetReason
watchdog
brownout
PMIC
Vol
```

需要回答：

- 黑屏前 MCU 是否仍持续记录日志；
- MCU 是否主动要求 SoC OFF；
- SoC 电源轨或复位信号是否发生变化；
- MCU 自身计数是否归零；
- MCU 是一直运行，还是与 SoC 一起停止；
- MCU 重启后何时重新执行 SoC ON；
- 电压是否出现可疑下降。

判断“整个 IVI 突然断电”时，必须比较 MCU、PVM、GVM 的实际末条日志。PVM 和 GVM 的最后时间不要求毫秒级一致，但应考虑各自缓存、刷盘频率和日志采集链路。如果 MCU 仍连续运行，应进一步判断是 SoC 单独掉电、SoC reset、SoC hang，还是 PVM/GVM 日志通道失效。

## 10. 第七步：检查 PVM 电源状态机和 STR 路径

重点搜索：

```text
Power/EFSM/mode
UsageMode
STANDBY_ALARM
STANDBY
GUARDMODE
NORMALMODE
POWER_MODE=1
STR
PRE_SUSPEND
POST_SUSPEND_ENTER
PM: suspend entry
PM: suspend exit
SHUTDOWN_CANCELLED
CANCEL_STR
vmm_request_gvm_pwr_key
```

若 PVM/qcrosvm 正常请求暂停或停止 GVM，理论上应存在：

1. PVM 电源状态迁移；
2. 发往 GVM 的 power/suspend 请求；
3. GVM ACK、失败或超时；
4. qcrosvm/Gunyah 状态变化；
5. PVM 自身 suspend 的进入或取消序列。

若负责记录这些事务的 PVM 日志在关键窗口之前已经截断，只能写“该路径无法验证”，不能写“没有执行该路径”。

## 11. 第八步：检查 GVM Android 电源链路

重点检查：

- VHAL 原始 property ID、value 和 timestamp；
- UsageMode；
- `handlePower`；
- ACC ON/OFF；
- `mPowerState`；
- `ScreenModePowerPolicy`；
- Android AP power state；
- suspend/shutdown 请求；
- system_server、SurfaceFlinger、HWC、SystemUI；
- ANR、native crash、watchdog、kernel panic。

必须把事件链拆开：

```text
原始车辆信号
  -> VHAL property
  -> Android 电源策略
  -> 屏幕 OFF/ON 请求
  -> 软件确认
  -> 物理屏幕实际状态
```

不要只引用 `handlePower`，应同时保留它前面的 VHAL property 作为直接输入证据。

## 12. 第九步：检查 qcrosvm/Gunyah

重点搜索：

- VM start/stop/pause/resume；
- VM exit reason；
- vCPU watchdog；
- Gunyah Resource Manager 错误；
- guest shutdown、crash 或重建；
- VIPC/RPC 断开；
- shared memory、SMMU、IRQ、virtio 异常；
- GVM suspend 请求及 ACK/timeout。

若 GVM 日志突然停止而 PVM 继续运行，应优先确认：

1. GVM 是否真的停止；
2. 只是 logcat/日志服务停止，还是整个 guest 停止；
3. qcrosvm 进程是否仍在；
4. GVM vCPU 是否仍被调度；
5. PVM 是否还能与 GVM 通信。

## 13. 第十步：检查两个屏幕的显示链路

### 13.1 仪表侧

- Tuanjie 心跳、场景和渲染日志；
- coreservice 信号输入；
- openwfd/display server；
- MDSS/DRM/HWC；
- layer、buffer、commit、flush；
- 仪表 panel、背光和 SerDes。

### 13.2 中控侧

- Android DisplayManager；
- WindowManager；
- SurfaceFlinger；
- HWC/display HAL；
- SystemUI；
- `ScreenModePowerPolicy`；
- GVM 到 PVM 显示后端的连接；
- 中控 panel、背光和 SerDes。

### 13.3 共同链路

如果 PVM 和 GVM 都继续正常产生日志和画面提交，而两个物理屏幕同时黑，应优先调查：

- 公共显示电源；
- 背光控制；
- display controller；
- openwfd/display backend；
- SerDes/链路训练；
- panel reset；
- MCU 对显示电源或背光的控制。

## 14. 第十一步：反向分析恢复链路

从恢复操作开始反向追踪：

1. 方控或其他恢复事件最先到达哪个域；
2. MCU 是否执行 reset 或 SoC OFF/ON；
3. PVM 是 suspend resume，还是完整 boot；
4. qcrosvm 是否重新创建 GVM；
5. GVM 是 resume，还是完整 Android boot；
6. 仪表和中控分别在哪一步恢复；
7. 恢复前旧实例是否还存在活动迹象。

判断完整重启时，应使用 boot banner、boot ID、PID、服务初始化和 VM 创建记录，而不是仅凭屏幕出现开机画面。

## 15. 快速判断矩阵

| 观察结果 | 优先调查方向 |
| --- | --- |
| PVM、GVM 日志持续，两个屏都黑 | 公共显示后端、背光、SerDes、显示供电、错误屏幕策略 |
| GVM 停止，PVM/Tuanjie 持续 | GVM/qcrosvm；仪表也黑时同时检查 PVM 显示后端 |
| PVM、GVM 几乎同时突然停止，MCU持续运行 | SoC 掉电、SoC reset/hang、PVM崩溃、公共日志链路失效 |
| MCU明确记录 SoC OFF，随后 PVM/GVM停止 | MCU或整车电源策略导致 SoC 下电 |
| MCU内部计数归零并重新初始化 | MCU发生重启；继续确认它与SoC重启的先后关系 |
| 三个域日志均持续且画面仍在提交 | 物理显示、背光、panel或SerDes链路 |
| 只有PVM聚合syslog停止，其他PVM日志继续 | syslog/落盘链路中断，不能认定PVM停止 |
| 有完整STR请求、ACK、suspend entry/exit | 正常或异常低功耗路径，继续核对返车取消和恢复 |
| 缺少STR日志且关键窗口未被保存 | STR路径不能确认，不能直接排除 |

## 16. 根因假设排序

建议逐项验证以下假设：

1. MCU/PMIC 导致 SoC 突然掉电或复位；
2. PVM kernel、watchdog 或硬件异常导致整个 SoC 计算域停止；
3. PVM 电源状态机错误继续进入低功耗；
4. qcrosvm/Gunyah 错误暂停或停止 GVM；
5. PVM 公共显示后端、背光或 SerDes 使两个屏同时无输出；
6. GVM Android 电源或显示策略异常；
7. 单一应用/SystemUI 异常。

两个屏幕同时黑时，单一 Android 应用异常通常不是最高优先级，但仍需用日志而不是概率将其排除。

## 17. 最终报告结构

建议最终报告至少包含：

1. **结论摘要**：只列已证实结论和最关键限制；
2. **日志范围与完整性**：说明有哪些文件、缺哪些窗口；
3. **时钟对齐方法**：列出跨域锚点和偏差；
4. **故障时间线**：每行附文件名、行号和原始日志；
5. **各域最后日志矩阵**：MCU、PVM、GVM分别列出；
6. **电源链路分析**；
7. **显示链路分析**；
8. **qcrosvm/Gunyah分析**；
9. **恢复链路分析**；
10. **根因假设及证据等级**；
11. **证据缺口和下一次补采建议**。

## 18. 下一次建议补采的持久化证据

当现有日志不能定因时，建议补充：

- MCU 在 reset 前持久化的 reset/power/watchdog 状态；
- PMIC reset cause、SoC power-good 和关键电源轨状态；
- PVM pstore/ramoops；
- GVM pstore；
- qcrosvm/Gunyah 持久化环形日志；
- powermgr/STR 事务日志；
- display/openwfd/DRM/HWC 持久化日志；
- panel、背光和 SerDes 状态；
- MCU、PVM、GVM 可关联的统一事件序号；
- 故障前后 CAN Trace；
- 必要时增加 GPIO、电源轨或 reset 线示波器波形。

## 19. 核心原则

```text
先找两个屏幕的共同上游，再查单独的 GVM Android。
先确认各域真正的最后日志，再判断掉电、挂死、休眠或日志丢失。
先验证正常电源/VM事务应有的完整日志序列，再讨论正常暂停或停止。
每个结论都保留文件名、行号和原始日志，并明确证据等级。
```
