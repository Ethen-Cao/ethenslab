# 故障根因分析报告（RCA）

目标是说明“什么条件下，哪个对象为何偏离预期，如何造成故障和影响，以及如何证明修复有效”。证据不足时交付明确标注缺口的阶段性报告，不为填满模板补造结论。

编写或更新报告前，完整读取 [报告模板](assets/rca-report-template.md)。默认使用中文 Markdown，保留模板的元信息、五个编号章节及“评审与闭环判据”；按实际增删表格行，不扩展成无关的通用排障教程。用户指定的格式、输出位置和范围优先。

## 输入与工作边界

- 先识别问题范围、发生场景、预期与实际、影响对象、故障版本和已有材料。区分进程退出、VM 终止、OS 重启和整机复位，不把它们统称为“系统重启”。
- 缺失事实填写“未知”；原因或因果关系尚无足够证据时标“待验证”；负责人和期限未安排时分别写“待指定”“待定”。不要推算不存在的故障次数、版本、时间、责任人或实验结果。
- 只就会改变故障范围、原因判断或整改方案的关键信息提问；其他缺口写入报告并继续。证据无法获得时，明确缺失内容、获取方式或客观限制，不反复追问后仍输出确定结论。
- 采用已有材料和任务授权范围内的检查结果。验证计划与已执行实验分开；提出验证或整改措施不意味着已经执行。
- 更新既有报告时保留可用内容及稳定的 R#、E# 编号；新证据追加编号，结论变化说明依据。审查请求默认指出具体段落、关系和证据缺口，不自动重写原文。

## 从事实建立因果关系

1. **定义可观测故障。** 将“卡死、泄漏、风暴”等词落实到判据，例如响应超时、资源随时间增长或单位时间事件数。写清对象、时间、次数／样本数或统计窗口；不能从单次截图推断发生率。
2. **提炼证据并分配 E#。** 每条证据包含来源定位、关键事实和适用范围。日志记录文件、时刻和进程／VM／设备等标识；源码记录对应版本、路径及函数或行号；实验记录版本、条件、对照与实际结果。缺失定位明确标注，不猜行号或版本。原始材料放附件或引用位置，正文保留支撑判断的必要片段。
3. **逐段建立 R#。** 每行解释“前因如何改变状态并导致后果”，写出调用、资源、数据或时序机制，关联 E# 并独立判定。共同触发条件写“同时满足”；分支传播分别列出，不能强行串成一条链。
4. **区分原因与处置。** 分清触发条件、根因候选、促成／放大因素、直接故障、检测／恢复动作和用户影响。模板中对错误码、资源耗尽、`abort`、watchdog 复位等“继续解释其形成原因”的要求，是要求继续调查；查到证据边界时，将缺口写入验证计划并保留“待验证”，不要臆造更深一层原因。
5. **检查证据是否覆盖本次事件。** 源码通常证明某机制可能发生，还需证据说明相关条件和路径在本次故障中成立。时间先后、日志相邻、一次修复后未复现或同一事实被多次转述，均不能单独证明因果。跨进程／VM／设备关联时核对对象、实例、版本及时间基准。
6. **保留竞争解释和反证。** 对影响判断的其他可能原因给出可区分的验证方法；已排除项引用反证 E#。缺少日志或实验未复现，不自动等于假设被排除；与结论冲突的主要证据必须得到解释。
7. **据此撰写当前结论。** 使用模板中的“触发条件 → 具体原因 → 作用机制 → 直接故障 → 用户影响”表述。第 2 节的断言不能强于第 3 节的证据；仅部分关系成立时，逐项说明已证实部分和待验证边界。

## 验证与整改

- 第 4 节只列影响原因判断或整改选择的疑点，关联 R# 或明确假设。方法写到可以执行和判定：观察什么、如何对照、什么结果支持、什么结果推翻或要求修正假设。避免“继续分析”“增加日志”而没有目标和判据。
- 第 5 节区分根因修复与防护／预防，每项对应具体原因或传播环节。重试、重启、扩大资源等缓解措施的作用范围要说清楚，不能凭缓解有效就判定根因已修复。针对未证实原因的措施标为候选方案。
- 在验收前明确验证版本、场景与负载、轮次或时长、关键指标及阈值、回归范围；不得在看到结果后倒推一个“通过”标准。不适用的维度或措施说明理由；尚未确定的标准保留待定项。
- “标准”和“实际结果”分别填写。结果引用实验 E#；未执行或证据不足写“待验证”。提交代码、完成部署或短期未复现，不能单独作为验证通过的依据。

## 状态与交付检查

原因状态和整改状态独立维护，不因一个状态推进而自动推进另一个。使用模板规定的状态：

实施或部署情况未知时，整改状态可暂列“待实施（实施情况待核实）”；明确这是尚未完成确认的流程状态，不能将缺少部署证据写成已证明未部署。

| 状态 | 判定要求 |
| --- | --- |
| 原因：待验证 | 关键因果关系仍有缺口，或主要反证尚未得到解释；可同时列出已经证实的局部关系 |
| 原因：已证实 | 从原因到用户影响的关键关系均有证据支持，机制在本次事件中成立，没有影响结论的待验证缺口 |
| 整改：待实施 | 必要措施尚未实施完成；有多项措施时逐项记录，汇总反映尚未完成的必要项 |
| 整改：待验证 | 必要措施已实施，但验收未完成、证据不足或未达到标准；失败结果须明确记录，补充整改需要再实施时更新相应状态 |
| 整改：验证通过 | 必要措施已实施，实际结果满足事先明确的验收标准，并有结果证据 |

交付前按模板的“因果成立、原因已证实、整改验证通过、问题闭环”四条判据检查。确认所有 R#／E# 引用存在、摘要与表格判定一致、关键疑点进入验证计划、必要措施对应原因且有验收标准。

保留未知和待验证项，清除未填写的 `【】` 占位符及纯填写提示。只有原因已证实、必要整改验收通过，且遗留事项明确负责人和处理结论，才能写“问题闭环”。遵守用户要求的脱敏范围，保留证据编号与必要的追溯关系。
